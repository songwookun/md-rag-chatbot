## 어떻게 여기까지 왔나

### Phase 0 — 문제의 크기부터 다시 쟀다

실험②의 지표(**보류여유** = 정답있음 최저 − 정답없음 최고)는 **극단값 두 개**가 부호를 정하고,
**부호밖에 알려주지 않는다.** 그래서 임계값과 무관한 지표를 하나 더 놓았다.

```
보류AUC = P(답할 수 있는 질문의 점수 > 답이 없는 질문의 점수)
```

결과는 **0.947**. *"90여 설정 전부 음수"* 는 사실 *"전부 AUC < 1"* 이었고,
가망 없는 0.6대가 아니라 **한 군데 누수**였다. 57쌍 중 뒤집힌 건 3쌍뿐이었다.

> ⚠ 처음엔 `보류여유 > 0 ⟺ 보류AUC = 1.0` 이라고 적었는데 **틀렸다. 역은 성립하지 않는다.**
> 여유는 정답 노트 중 **최저점**, AUC 는 **최고점**을 쓴다. 복수정답 질문에서
> 두 번째 정답이 낮으면 AUC 1.0 인데 여유가 음수가 된다. Phase 2D 에서 실제로 그랬다.

### Phase 2A — BM25 가설, 기각

*"질문의 용어가 노트에 0회면 어휘 검색은 0점일 것"* 이라 봤다. **5.488점이 나왔다.**
토큰화가 `LLM-as-a-judge` 를 `llm`·`as`·`a`·`judge` 로 쪼갰고, `llm` 은 그 노트에 잔뜩 있다.

> 비유 — "김치찌개"를 찾는데 검색기가 `김치` + `찌개` 로 나눠 찾는 것. 「김치볶음밥」이 걸린다.

**하마터면 잘못 채택할 뻔했다.** 하이브리드 RRF 의 보류여유가 −0.0256 → −0.0007 로
*"거의 성공"* 처럼 보였는데, **보류AUC 는 0.947 → 0.895 로 나빠졌다**(뒤집힌 쌍 3 → 8).
Phase 0 에서 지표를 하나 더 놓은 것이 여기서 회수됐다.

### Phase 2B — 희귀 토큰, 부분 성공

흔한 조각을 빼고 **볼트에 희귀한 토큰만** 봤다. `− OOV 페널티` 가 유일하게 살아남았다.

여기서도 지표에 속을 뻔했다. `− OOV 페널티` 의 AUC 가 떨어져 **회귀로 오해**했는데,
**질문별 순위가 원본과 100% 동일**했다. 문서와 무관한 상수를 질문마다 빼면
질문 안의 순서는 안 바뀌고, 다만 AUC 가 모든 (질문×문서) 쌍을 한 통에 넣고 비교해서
질문끼리의 스케일이 어긋난 것이었다.

> **질문별 변환에는 AUC 를 회귀 감시로 쓰면 안 된다.** R@k · MRR 로 봐야 한다.

### Phase 1 — 표본을 3개에서 28개로

여기까지의 모든 숫자가 **답 없는 질문 3개**에 걸려 있었다. 25개를 추가했다.

**결정 과정**(자세히는 노트북에):
- **25개** — 40개가 통계적으로 안정적이지만 **질문 품질이 떨어지면 그 안정성이
  오히려 잘못된 결론을 단단하게 만든다.** "품질을 통제할 수 있는 범위에서 최대".
- 답있음은 19개 유지 — 쌍이 57 → 532 로 늘어 이미 8배 안정된다.
- 후보는 AI 가 생성하고 **선택은 사람이** — AI 가 시스템 동작을 알아서 편향될 수 있다.
- **결과를 보고 질문을 고치지 않는다.**

**결론 여럿이 무너졌다.** `임베딩 × 희귀커버리지` 가 0.9649 → **0.6457** 로 폭락했다.
3개일 때 2등이던 게 꼴찌가 됐다. 반대로 베이스라인은 0.9474 → 0.9605 로 **올랐다**.

**층 정의도 틀렸다.** 용어 등장 횟수로 나눴는데, 실제로 점수를 정하는 건
*"질문 전체가 볼트의 중심 주제와 얼마나 가까운가"* 였다.
**객관적인 기준이라고 올바른 기준은 아니다 — 재현되게 틀렸을 뿐이다.**

### Phase 1-B — 왜 뚫리는지 진단

누수 6개 중 5개가 한 층(L3b)에 몰렸다. 원인은 두 겹이었다.

**노트 쪽** — 자석은 **"용어 정리" 노트**다. 한 노트가 수십 개 용어를 얕게 나열해서
어떤 기술 질문이든 조금씩 걸린다. **길이는 원인이 아니었다**(상관 −0.14).
47,813자 RAG 설명서가 자석일 거라 봤는데 상위 8개에도 없었다.

**질문 쪽** — 어휘의 **양**이 아니라 **성격**이 갈랐다.

| | 볼트 어휘 비율 | 그 어휘의 흔함 |
|---|---|---|
| 답있음 | 0.595 | 0.162 — **특정 노트를 지목하는 말** |
| 누수(L3b) | 0.336 | 0.299 — **아무 노트나 걸리는 말** |

`최고점 vs 어휘의 흔함` 상관 **+0.591**.

> 그래서 어휘 신호로는 못 푼다 — **누수 질문들은 볼트 어휘를 실제로 쓴다.**
> 남은 건 질문과 문서를 **같이 보는** 수단이다.

### Phase 2C — LLM 판정

*"이 노트에 이 질문의 답이 실제로 적혀 있나"* 를 그냥 물었다.
**답없음 28개 중 26개를 0점**으로 걸렀고, L1·L2·L3a 는 **전부 0.000** 이다.

그런데 단독으로는 못 쓴다. 점수가 이산적(0 · 0.2 · 0.5 · 1.0)이라 **순위를 못 매기고**,
단독 R@1 이 0.737 로 무너진다. 답있음 19개 중 2개도 오판했다.

**오판 3건을 확인하다 라벨 오류를 하나 찾았다.** `MSA vs 모놀리식 기준` 질문의
정답 노트에는 **정의만 있고 선택 기준이 없다**(`선택 0 · 기준 0 · 트레이드 0`). LLM 이 맞았다.
**고치지 않고 남겼다** — 결과를 보고 라벨을 바꾸면 데이터에 맞춰 실험을 조정하는 것이 된다.

> 다음 실험의 숙제: *"용어 정의가 있으면 '기준을 묻는 질문'의 답으로 볼 것인가."*

### Phase 2D — 크로스인코더 리랭커

보류AUC **1.0000**, 층 누수 **0/28**, R@1 **1.000**, **API 0회**.
부트스트랩 2000회 전부 1.0 — 임베딩 단독의 구간이 [0.90, 0.996] 인 것과 대조된다.

LLM 판정을 안 쓴 이유는 성능이 아니라 **비용**이다 — 느리고(+약 15초 vs +2~10초),
매 요청 API 비용이 붙고, 순위를 못 매긴다.

## 풀었다 — 응답 시간 편차

위에 "다음에 볼 것"으로 적어둔 세 가지를 그대로 쟀다.

| 확인한 것 | 결과 |
|---|---|
| 워밍업을 배치 1~5개 전부 반복 | **효과 없음** — 1개만 데운 것과 동일 |
| 패딩을 512 로 고정 | **효과 없음** — 중앙 0.92 vs 0.97초 |
| CPU 강제 | **이게 답이었다** — 폭 1.0배 |

**재컴파일 가설은 틀렸다.** 결정적인 건 CPU 다. CPU 는 재컴파일을 하지 않는데도
"처음 보는 모양" 0.97초 vs "이미 본 모양" 1.02초로 **차이가 없었다.**
MPS 도 마찬가지였다. 실재하는 건 **첫 호출 1회 초기화**(9~15초)뿐이고,
그 뒤로는 문서 개수에 선형이다.

```
문서   1개    2개    3개    4개    5개
MPS   0.40  0.60  1.00  1.25  1.60초      문서당 ~0.3초
```

진짜 원인은 **MPS 추론을 메인 스레드 밖에서 돌린 것**이었다.
이벤트 루프를 안 막으려고 넣은 `to_thread` 가 편차를 만들고 있었다.

```
메인스레드 직접     중앙 1.95 · 최대 2.59초
asyncio.to_thread  중앙 2.28 · 최대 7.90초   ← 튄다
전용 스레드 1개     중앙 2.51 · 최대 5.87초   ← 고정해도 튄다
```

### 고친 방법 — `RERANK_DEVICE=cpu` 를 기본으로

| 장치 | 중앙 | 최대 | 폭 |
|---|---|---|---|
| cpu | 2.31초 | 2.41초 | **1.0배** |
| mps | 1.92초 | 2.06초 | 1.2배 — 다른 회차에서 **7.9초**까지 |

중앙값은 mps 가 0.3초 빠르지만, 목표를 깨는 건 중앙값이 아니라 **꼬리**다.
그리고 도커/클라우드에도, 이 저장소를 클론한 대부분의 기계에도 mps 는 없다.
기본을 cpu 로 두면 문서에 적은 숫자가 그 사람들에게도 참이 된다.

### 실제 파이프라인 재측정 (질문 9회)

| 구간 | MPS (전) | CPU (후) |
|---|---|---|
| 검색 (임베딩 + Pinecone) | 1.4 ~ 3.7초 | 0.7 ~ 2.9초 |
| 원본 로드 (GitHub 5개 병렬) | 0.4 ~ 0.7초 | 0.3 ~ 0.8초 |
| **재순위** | **4.0 ~ 10.4초** | **2.9 ~ 5.2초** |
| 생성 (Gemini) | 3.1 ~ 4.2초 | 2.3 ~ 3.8초 |
| **합계** | **6.6 ~ 16.0초** | **5.2 ~ 10.6초** |

보류로 끝나는 질문은 5~6초다(생성을 안 부르므로).

> **또 지표에 속았다 — 이번이 여섯 번째다.**
> 합계만 보고 리랭커 탓을 했다. 구간을 나눠 재기 전까지는 검색이 3.7초씩 걸린다는 것도,
> 편차의 정체가 스레드라는 것도 몰랐다. 실험 내내 "자를 잘못 골랐다"고 적어놓고
> **측정하지 않은 것을 원인으로 지목**했다.

## 표현 민감도 — 서버에 넣고서야 드러난 한계

브라우저에서 직접 물어보다 발견했다. 같은 뜻을 네 가지로 물었다 (컷 `0.20`):

| 질문 | 최고점 | 결과 |
|---|---|---|
| LLM 토큰 비용 계산해서 월 예산 잡는 법 | 0.1728 | 보류 |
| LLM 토큰 비용 계산해서 월 예산 잡는법 **알려줘** | **0.2879** | 통과 |
| LLM 토큰 비용 계산법 | 0.8369 | 통과 |
| 토큰 비용 어떻게 계산해? | 0.3550 | 통과 |

넷 다 같은 노트(`LLM-핵심-용어`)를 최고점으로 골랐다.
첫 줄의 `0.1728` 이 실험③에서 **답없음 최고점**으로 기록된 바로 그 값이다.

**"알려줘" 세 글자가 점수를 +0.115 움직였다. 그런데 경계 여유는 0.069다**
(답있음 최저 0.242 − 답없음 최고 0.173). 표현 하나가 만드는 흔들림이
경계 전체보다 1.7배 크다.

> **보류AUC 1.0000 은 "이 47개 문장"에 대한 값이지 "이 47개 질문"에 대한 값이 아니다.**
> 부트스트랩 2000회가 전부 1.0 이었던 것도 이걸 못 잡는다 —
> 부트스트랩은 같은 문장을 다시 뽑을 뿐, 문장을 바꾸지 않기 때문이다.
> 표본 수를 늘려도 안 보이는 종류의 취약점이다.

### 그래도 지어내지는 않았다

통과한 답변의 실제 출력:

> 저장된 노트에 월 예산을 잡는 **구체적인 방법은 명시되어 있지 않습니다.**
> 다만 토큰 비용에 대한 다음 내용이 있습니다 — `비용 = 토큰 수 × 단가`
> `[[LLM-핵심-용어-및-아키텍처-설계-가이드]]`

없는 건 없다고 말하고, 있는 것만 근거와 함께 냈다. **그라운딩 프롬프트는 제 역할을 했다.**
그리고 `LLM 토큰 비용 계산법` 이 0.8369 인 것은 **오판이 아니다** — 그 노트에
계산식이 실제로 있다. 즉 네 줄 중 진짜 문제는 두 번째 하나다.

### 임계값으로는 못 푼다

`0.2879` 를 막으려면 컷을 `0.30` 으로 올려야 하는데,
**답있음 최저가 `0.242`** 라 진짜 답을 보류하게 된다. 두 분포가 겹치는 자리다.
실험②에서 임베딩 임계값에 대해 내린 결론과 같은 모양이 리랭커에서도 반복된다.

### 다음 실험의 과제

- 질문마다 **표현 변형 3~5개**를 만들어 다시 측정한다 (표현에 강건한 보류AUC)
- 라벨 정책을 정한다 — **부분 답변**을 누수로 볼 것인가, 정직한 답으로 볼 것인가.
  실험③에 남겨둔 숙제(*"용어 정의가 있으면 기준을 묻는 질문의 답으로 볼 것인가"*)가
  실제 사례로 돌아온 것이다.
