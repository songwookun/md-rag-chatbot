# 실험② 스윕 — 왜 이 설정을 선택했는가

> 2026-08-02 · 노트북 `notebooks/02_sweep.ipynb`
> 설정 90여 개 비교 · 임베딩 1,400여 건

---

## 이 실험을 한 이유

실험①은 `task_type` 4조합만 봤고, 지표가 **분리도(관련 평균 − 무관 평균)** 하나였다.
"현재 코드보다 나은 게 있나"에 답하려면 축과 지표를 둘 다 넓혀야 했다.

**축 4개** — task_type(8×8) / 임베딩 대상(9종, 청킹 포함) / 차원(4종) / 임계값(66단계)
**지표 6개** — AUC · R@1,3,5 · MRR · F1 · 보류여유

---

## 결정 1 — 지표를 분리도에서 AUC로 바꿨다

### 왜 바꿨나

분리도는 **평균의 차이**만 본다. 그런데 평균이 멀어도 분포의 꼬리가 길게 겹치면 실제로는 못 가른다.
반대로 평균이 가까워도 깔끔하게 갈리면 잘 작동한다. **평균은 겹침을 못 잡는다.**

AUC는 "무작위로 뽑은 관련 쌍이 무작위 무관 쌍보다 점수가 높을 확률"이다.
모든 쌍을 비교하므로 겹침이 그대로 반영되고, **임계값과 무관**하다.
임계값 튜닝과 분리해서 **임베딩 설정 자체의 능력만** 잴 수 있다.

### 바꾸고 나서 드러난 것 — 실험①의 결론을 수정한다

| | 실험① 판정 | 실험② 재측정 |
|---|---|---|
| 현재 코드 | 분리도 **0.103** → "잘 안 갈린다" | AUC **0.982** → 매우 잘 갈린다 |
| | | R@3 = **1.00** (상위 3개 안에 항상 정답) |

**검색은 원래 잘 되고 있었다.** 분리도가 낮아 보였던 건 지표가 조잡했기 때문이다.

> **원리**: 지표가 틀리면 결론도 틀린다. "성능이 나쁘다"고 결론 내리기 전에
> **그 지표가 내가 알고 싶은 걸 재고 있는지** 먼저 의심해야 한다.

## 결정 2 — 차원을 3072 → 768로 줄인다 ✅ 채택

### 무엇을 물었나

`.env.example`은 Pinecone 인덱스를 3072차원으로 만들라고 한다. **정말 필요한가?**
차원은 곧 **저장 비용과 검색 시간**이다.

### 데이터

| 차원 | AUC | R@1 | 저장량 | 3072 대비 손실 |
|---|---|---|---|---|
| 3072 | 0.9907 | 0.947 | 100% | — |
| 1536 | 0.9910 | 1.000 | 50% | **+0.0003** |
| **768** | 0.9898 | 0.947 | **25%** | **−0.0010** |
| 256 | 0.9841 | 1.000 | 8% | −0.0067 |

현재 코드 조건(요약/DOC-QUERY)에서 3072 → 768:

```
AUC   0.982 → 0.982   (변화 없음)
R@1   0.947 → 1.000   (오히려 개선, 단 한 문제 차이라 노이즈일 수 있음)
저장량 100%  →  25%
```

### 왜 손실이 없나

`gemini-embedding-001`은 **MRL(Matryoshka)** 방식이라, 앞쪽 차원에 중요한 정보가 몰려 있다.
뒤를 잘라내도 핵심이 남는다. 그래서 3072의 4분의 1만 써도 성능이 유지된다.

### 함정 하나 — "정규화가 필요하다"는 말

차원을 줄이면 벡터의 L2 노름이 1이 아니게 된다 (1536→0.695, 768→0.588).
문서에서 "축소 시 재정규화 권장"이라고 하는 이유다.

**그런데 코사인 유사도에는 영향이 없다.**

```
cos(a,b) = (a·b) / (|a| × |b|)
```

이미 크기로 나누고 있다. 벡터에 상수를 곱해도 값이 같다.
**정규화가 필요한 건 내적(dot product)을 유사도로 쓸 때**다.

> **원리**: 권장사항을 그대로 따르기 전에 **내 상황에 해당되는지** 확인한다.
> Pinecone 인덱스를 `cosine` metric으로 만들었으면 이 권장은 나와 무관하다.

### 판단

**채택.** 저장량 4분의 1에 성능 손실 0.1% 미만. 근거가 명확하다.
바꿀 곳은 Pinecone 인덱스 재생성 + `output_dimensionality=768` 한 줄.

## 결정 3 — 임계값 0.6 → 0.65 ✅ 채택

### 무엇이 문제였나

실험①에서 **무관 쌍의 평균이 0.608**이었다. 임계값 0.6보다 높다.
0.6이 골짜기가 아니라 **산 중턱에 그어진 선**이었다.

그리고 답이 볼트에 없는 질문 3개가 **전부 0.6을 통과**했다.

```
0.686  LLM-as-a-judge 평가 파이프라인?  → LLM-핵심-용어-가이드.md
0.655  BM25 하이브리드 검색?            → AXswgBrain-기술-설명서.md
0.639  vLLM LoRA 파인튜닝?             → AXswgBrain-기술-설명서.md
```

즉 **"저장된 노트에 없습니다"라고 답해야 할 때 엉뚱한 노트를 근거로 답을 지어낸다.**

### 데이터

임계값 0.30~0.95를 훑은 결과:

- **0.65** — 답 없는 질문 3개를 모두 차단. 그때 재현율 80%, 오통과율 2.2%
- Youden's J 최적값 = 0.633 (두 오류를 같은 비중으로 볼 때)

### 판단

**0.65 채택.** 다만 이건 **완전한 해결이 아니다** — 재현율 80%는 정답의 20%를 놓친다는 뜻이다.
아래 결정 5로 이어진다.

## 결정 4 — task_type과 청킹은 **바꾸지 않는다** ❌ 보류

여기가 이번 실험에서 가장 중요한 판단이다. **1등을 채택하지 않기로 했다.**

### 데이터가 말한 것

`task_type` 64조합에서 현재 코드(DOCUMENT/QUERY)는 **40등**이었다.
1등은 `FACT_VERIFICATION / QUESTION_ANSWERING`. 표현에 청킹을 쓰면 AUC 0.991로 가장 높다.

| 설정 | 벡터수 | 저장량 | AUC | R@1 | F1 |
|---|---|---|---|---|---|
| A 현재코드 요약/DOC-QUERY/3072 | 20 | 1.00 | 0.982 | 0.947 | 0.549 |
| B task만 변경 /FACT-QA/3072 | 20 | 1.00 | **0.972** | 1.000 | 0.630 |
| E 청킹 제목+청킹1000/1536 | **150** | **3.75** | **0.991** | 1.000 | 0.806 |
| **F 현재 + 차원만 768** | 20 | **0.25** | 0.982 | 1.000 | 0.581 |

### 왜 안 바꾸나

**① 차이가 "한 문제" 수준이다**

정답이 있는 질문이 **19개**뿐이다. R@1 0.947 vs 1.000은 **질문 하나** 차이다.
표본 밖에서도 유지될 차이라고 볼 근거가 없다.

**② task_type 최적이 표현에 따라 뒤집혔다**

- 원문전체 기준: `FACT_VERIFICATION`이 1등 (AUC 0.986), 현재 코드 0.968
- **요약 기준**: 현재 코드가 더 높음 (0.982), `FACT-QA`는 0.972

축을 하나씩 고정해 최적을 찾는 **그리디 탐색**의 한계가 그대로 드러났다.
실제 코드는 요약을 임베딩하므로, **요약 기준에서는 현재 설정이 이미 좋다.**

**③ 청킹은 성능 이득보다 비용이 크다**

AUC +0.009를 얻는 대가가 **벡터 7.5배, 저장량 3.75배**다.
게다가 청킹은 코드 구조를 바꾼다 — 노트 하나가 벡터 여러 개가 되므로
`upsert`, 검색 결과 집계, 원본 로드 로직이 전부 달라진다.

> **원리**: 순위표 1등이 곧 채택 대상이 아니다.
> **(성능 이득) vs (비용 + 복잡도 + 표본 신뢰도)** 를 같이 놓고 봐야 한다.
> 표본이 작을수록 "안 바꾼다"가 안전한 선택이다.

### 판단

**보류.** 노트가 100개쯤 쌓이면 다시 잰다. 그때는 차이가 노이즈인지 실체인지 판별된다.

## 결정 5 — abstention은 임계값으로 해결 불가 ⚠ 구조 변경 필요

### 어떻게 알았나

**보류여유**라는 지표를 만들었다.

```
보류여유 = (정답 있는 질문의 최저 정답 점수) − (정답 없는 질문의 최고 점수)
```

이 값이 **양수여야** 임계값 하나로 "관련 있으면 통과, 없으면 차단"이 성립한다.
음수면 어떤 값을 골라도 둘 중 하나는 반드시 실패한다.

### 데이터

**측정한 90여 개 설정 전부 음수였다.** 최선이 −0.017 (청킹).

지표가 너무 엄격한 게 아닌지 의심해서, "질문당 정답 하나만 통과하면 된다"는
느슨한 기준으로 다시 계산했다. **결론은 같았다** (−0.026 → −0.023).

답 없는 질문 3개를 모두 막는 임계값(0.65)에서, 정답 있는 질문 19개 중 **16개만** 회수된다.

### 왜 이런가

볼트 20개가 **전부 AI/AX/개발 주제**다. 주제가 좁아서 어떤 질문이든 여러 노트와 의미가 가깝다.
"BM25 리랭커"를 물으면 RAG 기술서가 0.655로 걸린다 — **의미적으로는 실제로 가깝기 때문**이다.

임베딩은 "이 노트에 그 답이 실제로 있는가"가 아니라 **"주제가 비슷한가"**를 잰다.
그 둘은 다르다.

### 판단

**임계값 튜닝으로는 못 고친다.** 구조를 바꿔야 한다. 후보:

- **재순위화(rerank)** — 검색 후 교차 인코더로 다시 점수 매기기
- **하이브리드 검색** — 키워드(BM25) + 벡터 결합. "BM25"라는 단어가 노트에 없다는 사실을 활용
- **LLM 판정** — 상위 k개를 주고 "이 노트로 답할 수 있나"를 모델에게 묻기

> **원리**: 어떤 문제는 **파라미터가 아니라 구조**의 문제다.
> 숫자를 아무리 돌려도 안 되면 손잡이가 아니라 설계를 봐야 한다.
> 보류여유처럼 **"이게 가능하기는 한가"를 재는 지표**가 그 판단을 가능하게 한다.

## 시행착오 기록 — 처음엔 이렇게 접근했다

> **지우지 않는다.** 결론만 보면 "차원 줄이고 임계값 올림" 두 줄이지만,
> 거기까지 오는 데 틀린 접근이 여러 번 있었다. 그 과정이 진짜 내용이다.

### ① 지표를 잘못 골라서 "성능이 나쁘다"고 오판했다

**처음 접근** — 실험①에서 **분리도(관련 평균 − 무관 평균)** 하나로 판정했다.
결과가 0.103. 무관 평균이 0.608로 임계값 0.6보다 높았다.
→ **"검색이 잘 안 되고 있다"**고 결론 냈다.

**바꾼 것** — 실험②에서 AUC를 추가했다.

**그랬더니** — 같은 설정의 AUC가 **0.982**. R@3 = **1.00**.
상위 3개 안에는 **항상** 정답이 있었다. 검색은 원래 잘 되고 있었다.

**왜 이런 차이가 나나** — 분리도는 평균만 본다. 이 데이터는 관련·무관 점수가
전반적으로 다 높은 대신(볼트 주제가 좁아서) **순서는 정확했다**.
평균 차이는 작은데 순위는 거의 완벽한 상황을, 분리도는 "나쁨"으로 읽었다.

**교훈** — "성능이 나쁘다"고 결론 내리기 전에 **그 지표가 내가 알고 싶은 걸 재고 있는지** 먼저 본다.

### ② 범인을 잘못 지목했다

**처음 접근** — 무관 쌍 최고점 0.746을 보고 **"제목이 거의 같은 유사 노트 쌍일 것"**이라 예측했다.
(`개발-및-아키텍처-설계-핵심-용어-정리` vs `개발-아키텍처-설계-용어-정리`)

**확인해보니** — 상위 10개에 유사 노트가 **하나도 없었다.**

```
0.746  AX 엔지니어가 뭐 하는 직무야?   vs  AX-엔지니어-실무-기술-스택.md
0.736  RAG 챗봇 파이썬 라이브러리?     vs  AXswgBrain-RAG-챗봇-기술-설명서.md
0.727  AX 엔지니어가 뭐 하는 직무야?   vs  AX-엔지니어를-위한-AI-협업-개발-파이프라인.md
```

**진짜 원인** — 유사 노트가 아니라 **주제가 인접한 노트**였다.
볼트 20개가 전부 AI/AX/개발이라, 한 질문이 여러 노트에 동시에 걸린다.

**그래서 뭐가 달라졌나** — "중복 노트를 정리하면 된다"(데이터 정리 문제)에서
**"임베딩은 주제 유사도를 재지, 답이 있는지를 재지 않는다"**(구조 문제)로 진단이 바뀌었다.
결정 5(abstention 구조 변경)가 여기서 나왔다.

### ③ 안 일어날 문제를 미리 방어하려 했다

**처음 접근** — 볼트에 47,813자짜리 노트가 있어서 **토큰 상한에 걸릴 것**이라 예상.
텍스트를 잘라내는 로직을 준비했다.

**실제로** — 51,000자까지 그냥 통과했다.

**교훈** — 방어 코드를 미리 넣지 말고 **일단 돌려서 진짜 터지는지 본다.**
안 터지는 문제를 막는 코드는 복잡도만 늘린다.

### ④ 그리디 탐색이 뒤집혔다 — 하마터면 잘못 채택할 뻔했다

**처음 접근** — 축을 하나씩 고정하며 최적을 찾았다.
스윕1에서 **원문전체** 기준으로 `task_type`을 골랐고, `FACT_VERIFICATION`이 1등(AUC 0.986),
현재 코드는 **40등/64**(0.968)였다.
→ "현재 코드가 한참 나쁘다, `task_type`을 바꿔야 한다"고 판단할 뻔했다.

**바꾼 것** — 표현을 바꾼 뒤 `task_type`을 **다시** 확인하는 단계(스윕 2.5)를 넣었다.

**그랬더니** — 최적 조합이 바뀌었다.
그리고 **실제 코드가 쓰는 요약 표현** 기준으로 재보니:

```
요약 / DOC-QUERY (현재 코드)  AUC 0.982
요약 / FACT-QA   (1등이었던)  AUC 0.972   ← 오히려 낮다
```

**왜** — `task_type`의 효과가 **무엇을 임베딩하느냐에 따라 달라진다.**
원문 전체(수만 자)와 요약(수백 자)은 성격이 달라서, 원문에서 좋았던 게 요약에서는 아니었다.

**교훈** — 축이 서로 영향을 주면 그리디 탐색은 틀린다.
**앞 축을 다시 확인하는 단계**를 반드시 넣는다. 이번엔 실제로 뒤집혔다.

### ⑤ AUC 1등을 채택할 뻔했다

**처음 접근** — 스윕2 결과 `제목+청킹1000`이 AUC 0.991로 1등.
노트북의 최종 권고 코드가 자동으로 이걸 골랐다.

**다시 보니** — 벡터가 **150개**(요약은 20개), 저장량 **3.75배**.
AUC 이득은 **+0.009**. 그리고 청킹은 코드 구조를 바꾼다 — 노트 하나가 벡터 여러 개가 되어
`upsert`·검색 결과 집계·원본 로드가 전부 달라진다.

**바꾼 것** — 권고 코드에 **벡터수·저장량 컬럼**을 넣고, "1등 자동 채택"을 없앴다.

**그랬더니** — 아무도 예상 못 한 조합이 최선으로 드러났다.

```
A 현재코드      요약/DOC-QUERY/3072   저장 1.00  AUC 0.982  R@1 0.947
F 현재+차원만    요약/DOC-QUERY/768    저장 0.25  AUC 0.982  R@1 1.000
E 청킹         제목+청킹1000/1536     저장 3.75  AUC 0.991  R@1 1.000
```

**F** — `task_type`도 표현도 그대로 두고 **차원만 줄인 것**. 성능 유지, 저장 4분의 1.
탐색 대상 축 어디에도 "1등"이 아니었지만, 비용까지 넣고 보니 이게 답이었다.

### ⑥ 내가 만든 지표를 의심했다 (이건 검증에 성공)

**의심한 것** — 보류여유를 "관련 쌍 **전부**의 최저"로 정의했는데,
실제로는 질문당 정답 **하나만** 통과하면 답할 수 있다. **지표가 과하게 엄격한 것 아닌가?**

**확인** — 느슨한 기준("질문당 최고 정답 점수의 최저")으로 다시 계산했다.

```
엄격 기준  −0.026
느슨 기준  −0.023   ← 거의 같다
```

**결론은 같았다.** 지표가 엄격해서 나온 결과가 아니라 실제 문제였다.

**교훈** — 결론이 마음에 안 들 때 **지표를 의심하는 건 옳다.** 다만 의심했으면 **재계산해서 확인**해야지,
느낌으로 넘어가면 안 된다. 이번엔 확인했고 결론이 유지됐으므로 근거가 더 단단해졌다.

### ⑦ 캐시 없이 시작해서 500회를 태웠다

**처음 접근** — 실험① 노트북에 캐시 없이 임베딩을 바로 호출했다.

**그랬더니** — 그래프 레이아웃 한 번 고치는 데 **임베딩 168회 + 3분**.
같은 걸 세 번 재실행하며 **500여 회**를 태웠다. 코드는 한 줄도 안 바뀐 재실행도 있었다.

**바꾼 것** — `(텍스트, task_type, 차원)`을 키로 하는 파일 캐시를 넣었다.

**그랬더니** — 실험②는 설정 90여 개를 재면서도 첫 실행 이후 재실행은 **API 호출 0회**.
지표를 추가하거나 표를 바꿔도 즉시 나온다.

**키 설계 주의** — 텍스트만 키로 쓰면 같은 노트를 다른 `task_type`으로 임베딩한 걸 구분 못 해
**조용히 잘못된 벡터**를 돌려준다. `task_type`과 차원이 키에 반드시 들어가야 한다.

**교훈** — 반복 실험에서 캐시는 편의 기능이 아니라 **실험을 가능하게 하는 전제**다.
없으면 "설정 90개 비교" 자체를 시도조차 못 한다.

## 손노트로 옮길 원리 5개

1. **지표가 틀리면 결론도 틀린다.** 평균 차이는 분포의 겹침을 못 잡는다. 임계값과 무관한 지표(AUC)가 있어야 설정끼리 공정 비교가 된다.

2. **권장사항이 내 상황에 해당되는지 확인한다.** "차원 축소 시 정규화 권장"은 내적을 쓸 때 얘기다. 코사인은 이미 크기로 나눈다.

3. **1등을 자동 채택하지 않는다.** 성능 이득 옆에 비용·복잡도·표본 크기를 나란히 놓는다. 표본이 작으면 "안 바꾼다"가 안전하다.

4. **그리디 탐색은 축이 상호작용하면 뒤집힌다.** 축을 하나씩 최적화한 뒤 **앞 축을 다시 확인**해야 한다. 이번에 실제로 뒤집혔다.

5. **파라미터로 안 되는 문제가 있다.** "이게 가능하기는 한가"를 재는 지표(보류여유)를 만들어두면, 튜닝을 계속할지 설계를 바꿀지 판단할 수 있다.
